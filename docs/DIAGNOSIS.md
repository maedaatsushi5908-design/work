# 既存バックテスト（新高値ブレイク戦略）の診断

このリポジトリには既に `main.py` / `backtest.py` / `optimize.py` による
新高値ブレイク戦略のバックテストがある。`ev` を使ってその成績を検定した結果を
記録する。

**結論を先に書く。申告されている成績（総リターン301%、シャープ0.88）は、
真のエッジが完全に0でも再現できる水準である。**

---

## 1. 何が起きているか

### 診断の入力

| 項目 | 値 | 出典 |
|---|---|---|
| 申告年率シャープ | 0.88 | コミット `194316a`「シャープ0.82→0.88」 |
| 観測数 | 約2,470営業日 | `config.py` の 2015-01-01〜2024-12-31（約10年） |
| 試したパラメータ構成数 | 54 | `optimize.py` の `GRID` = 3×3×3×2 |
| 候補銘柄数 | 約4,000 | `config.py:50`「東証全銘柄スキャン」 |
| 選抜後の銘柄数 | 116 | `config.py:50`「品質フィルター済み116銘柄」 |

### 問題A — 銘柄ユニバースを結果で選抜している（最重要）

`config.py:50-51` に選抜条件が明記されている。

```python
# 東証全銘柄スキャン（full_scan_v2.py）から抽出した品質フィルター済み116銘柄
# 条件: 期待値プラス・化学/医薬/食品小売セクター除外・シグナル頻度≤9回/10年・平均株価≥500円
```

**「期待値プラス」がバックテスト期間の成績で判定されている。** つまり

1. 4,000銘柄で戦略を回す
2. 成績が良かった116銘柄を残す
3. **同じ期間で**その116銘柄をバックテストする

3の成績は、2で選抜した基準そのものである。良い成績が出るのは当然で、
それは戦略の性能ではなく選抜の産物である。

定量化するとこうなる。

```
$ python3 -m ev.cli diagnose --sharpe 0.88 --n-obs 2470 --trials 54 \
      --candidates 4000 --selected 116

選抜だけで生じる見かけの年率リターン: +23.12% (95%点 +23.91%)
選抜だけで生じる見かけの年率シャープ: +0.728
```

**真のエッジが完全に0の世界で、4,000銘柄から成績上位116銘柄を選ぶだけで、
年率+23%・シャープ0.728が現れる。** 申告値0.88のほとんどがこれで説明できる。

理論値とも一致する（上位α分位の標準正規の平均は φ(z_α)/α）。

```
α = 116/4000 = 0.029
z_α = Φ⁻¹(1−0.029) = 1.896
φ(1.896)/0.029 = 2.30
標本平均の標準誤差 = 0.02/√2470 = 4.02e-4
見かけのエッジ = 2.30 × 4.02e-4 × 252 = +23.3% / 年
```

さらに悪いことに、コミット履歴はこの選抜を**強化する方向に進んでいる**。

```
5b3f30a パラメータ最適化: 総リターン109%→223%、勝率41%→62%に改善
194316a 銘柄を30→55に拡張: 総リターン223%→301%、シャープ0.82→0.88
c21c8f9 スキャン対象を品質フィルター済み116銘柄に更新
```

「銘柄を増やしたら成績が上がった」は、通常なら分散効果で説明できない。
選抜候補を増やせば選抜バイアスが増えるので、これは**バイアスが強まった証拠**
として読むほうが自然である。

### 問題B — パラメータの過剰最適化

`optimize.py` は54通りのグリッドサーチを行い、最良構成を採用している。
その結果が `config.py` に反映されている。

```python
high_period: int = 195          # 260→195 に変更（最適化により）
stop_loss_pct: float = -0.10    # -0.08→-0.10
trailing_stop_pct: float = -0.20 # -0.15→-0.20
```

エッジが0でも54回引けば最大値は約2.2σ に達する。実際に**真のエッジ0の
54構成を模擬**すると、

```
エッジ0の54構成: グリッド最良の年率シャープ = 0.749
  ウォークフォワード検証期間の年率シャープ = +0.282
  パラメータ安定性 = 60%
```

**エッジが完全に0でも、54通り試せばシャープ0.749が出る。** 申告値0.88と
ほとんど区別できない。

多重検定補正をかけると申告シャープはこう減額される。

| 手法 | 調整後p値 | 調整後シャープ | 減額率 |
|---|---|---|---|
| Bonferroni | 0.317 | 0.320 | 63.7% |
| Holm | 0.317 | 0.320 | 63.7% |
| BHY | 1.000 | 0.000 | 100.0% |

### 問題C — 最適化のスコア関数が壊れている

```python
def score(r) -> float:
    return (r.sharpe_ratio * r.profit_factor * (1 + r.total_return)
            / (1 + abs(r.max_drawdown)))
```

シャープ × プロフィットファクター × 総リターンは、いずれもリターンの関数で
あり、**同じ情報を3回掛けている**。結果としてリターンの上振れを3乗で
評価してしまい、最も過剰最適化された構成が選ばれやすくなる。

またパラメータの安定性（近傍の構成も同じくらい良いか）を全く見ていない。
上のシミュレーションでパラメータ安定性が60%しかないのは、選ばれる構成が
期間によって変わる＝「最良パラメータ」が存在しないことを示している。

### 問題D — 合成データへの暗黙のフォールバック

`data.py` の `download_all_stocks` は先頭ティッカーの取得を試し、失敗すると
**全銘柄を合成データ（乱数ウォーク）に差し替える**。

```python
if not network_ok and use_synthetic_fallback:
    print("ネットワーク接続なし → 合成データモードで実行します")
    return generate_all_stocks(tickers, start_date, end_date)
```

標準出力に1行出るだけなので、`output/` のグラフや `trade_log.csv` を見ても
それが実データか乱数かは区別できない。「総リターン301%」が**完全な乱数の上で
計算された数字**である可能性を、成果物から排除できない。

### 問題E — シグナル過多時の銘柄選択が恣意的

`backtest.py` のエントリーループは `self.signals.items()` の辞書順で回り、
`max_positions` に達すると `break` する。

```python
for ticker, sig_df in self.signals.items():
    if len(positions) >= self.scfg.max_positions:
        break
```

`self.signals` は `stock_data` の挿入順（＝`CURATED_TICKERS` の記載順）で
構築されるため、同日に5枠を超えるシグナルが出た場合、常に**リストの上に
書かれている銘柄**が選ばれる。これは戦略ルールではなく実装の副作用であり、
`optimize.py` はこの副作用ごと最適化してしまう。銘柄リストの並べ替えだけで
バックテスト成績が変わる。

## 2. 総合

逐次控除すると次のようになる。

```
段階A: 選抜バイアスを控除    +0.880 − 0.728 = +0.152
段階B: 試行数54で Holm 補正  +0.152 → +0.000（減額100%）

残る年率シャープ: +0.000
```

**申告成績のうち、真のエッジに帰属できる部分は検出できない。**

これは「新高値ブレイク戦略に効果がない」ことの証明ではない。
**「このバックテストからは何も言えない」** ということである。

---

## 3. 何をすれば言えるようになるか

### 対策1 — ユニバースを成績で選ぶのをやめる

`config.py` の `CURATED_TICKERS` を破棄し、**事前に観測可能な構造的特徴だけ**で
ユニバースを決める。時価総額、売買代金、アナリストカバレッジ数、株価水準は
リターンと独立なので、選抜バイアスを生まない。

```bash
python3 -m ev.cli screen --csv universe.csv --portfolio 10000000
```

`ev.universe.screen_universe` は過去リターンを一切参照しない設計になっている。

### 対策2 — 学習期間と検証期間を分離する

`optimize.py` を検証期間に触らせない。学習期間だけでパラメータを決め、
検証期間は一度だけ使う。

```python
from ev.validation import walk_forward_grid

# {構成名: 日次リターン列} をグリッドサーチから作って渡す
result = walk_forward_grid(trial_returns, n_folds=5, min_train=600)
print(result.summary())
# → 「学習期間で最良を選ぶ」方針の正直な期待値が出る。グリッドの最良値ではない
```

### 対策3 — 試行数を必ず申告して割り引く

```python
from ev.validation import deflated_sharpe_ratio, probability_of_backtest_overfitting

print(deflated_sharpe_ratio(daily_returns, n_trials=54,
                            trial_sharpes=all_54_sharpes).summary())
print(probability_of_backtest_overfitting(trial_returns, n_blocks=10).summary())
```

PBOが0.5を超えていたら、パラメータ選択は害になっている。

### 対策4 — スコア関数を1つの指標にする

シャープ × PF × リターンをやめ、**検証期間のシャープ1つ**で評価する。
リターンの関数を掛け合わせても情報は増えず、過剰最適化だけが進む。

### 対策5 — 合成データフォールバックを明示的にする

`data.py` のフォールバックを既定で無効にし、合成データを使った場合は
出力ファイル名とグラフのタイトルに必ず `SYNTHETIC` を刻む。
黙って乱数に切り替わる仕組みは、それ自体が最大のバグである。

### 対策6 — 同日シグナルの選択ルールを明文化する

辞書順ではなく、構造スコア順・流動性順など**意図したルール**で選ぶ。
選択ルールも戦略の一部であり、最適化の対象に含めるなら試行数に数える。
