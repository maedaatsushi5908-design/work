# 数量計算書 転記マクロ

Excel の数量計算書の転記を自動化する。入れる前に必ず確認画面を出し、
書き込む前にバックアップを取る。

```
excel/vba/src/          保守用。ここを直す
  M_Hasai.bas             06 用。舗装版破砕を舗装厚で照合して転記（単独で動く）
  M_Util.bas              01 用の共通処理
  M_Config.bas            01 用。転記定義シート
  M_Engine.bas            01 用。転記元セルの解決
  M_Main.bas              01 用。照合・転記の入口

excel/vba/dist/         貼り付け用。src から生成する
  M_Hasai.bas             06 に貼る1ファイル（592行）
  M_Tenki.bas             01 に貼る1ファイル（1079行）
  sjis/                   同じものの Shift-JIS 版（インポート用）
```

`src/` を直したら `python3 excel/docs/build_vba.py` で作り直す。

# M_Hasai － 舗装版破砕の転記

マクロは1本だけ。

```
舗装版破砕を転記する()
```

入れる数式もこれだけ。

```
=SUMIF('試掘（舗50'!$O$11:$O$17,'総括表（土工事）'!$I14,'試掘（舗50'!$P$11:$P$17)
        └ 転記元の舗装厚欄      └ 総括表の厚さ欄      └ 転記元の合計欄
```

## なぜ SUMIF なのか

転記元の舗装厚は、その工事に出てくる厚さだけが**詰めて並ぶ**。

```
試掘（舗50 の □舗装版破砕工
  行11  As  4cm   0.0
  行12  As  10cm  1.2      ← 5cm が無いので 10cm が2行目に来る
```

`='試掘（舗50'!P12` のように行を固定していると、別の厚さの数量を拾う。
総括表の厚さ欄（I列）と一致する行だけを合計すれば間違えない。

転記元の厚さ欄は `INDEX/MATCH` で毎回組み替わるので、
**目で見ても行がずれていることに気づけない。** そこが危ないところ。

## やっていること

1. 総括表の、いちばん左の工種名が「舗装版破砕」の行を集める（13〜67行）
2. その行の**舗装厚**（工種名より左の列の右端にある数値）と
   **種別**（同じ範囲にある As / Co の字）を読む
3. 下の対応表にある列のうち、**黄色く塗ってあるセル**にだけ数式を入れる
4. As の行は転記元の As 側、Co の行は Co 側、As・Co の行は両方を足す

黄色は「入力セル（各数量計算書の数量を転記間違いないように！）」という
総括表の凡例そのままで、**どこに値が入るかは作成者が塗り分けている**。
推測せずにそれに従う。行26以降は口径ごとに別ブロックへ分かれるが、
塗り分けがそのまま境界になっている。

## 工事が変わったら直すところ

マクロの先頭にこれだけ置いてある。

```vba
Private Const TARGET_SHEET As String = "総括表（土工事）"

Private Const COL_MAP As String = _
    "J=試掘（舗50|" & _
    "K=試掘（舗300|" & _
    ...
    "U=管工（舗600"
```

見出しの口径（`PE50-300`）とシート名の口径は機械的に対応が付かないので、
**推測させずに書いてある**。使わない列は書かなくてよい。
`給水2度` は舗装版破砕のブロックが無いので入れていない。

対応表は実行前の確認画面にそのまま出る。ブロックが見つかったかどうかも
一緒に出るので、貼り間違いはそこで気づける。

```
 J列 → 試掘（舗50    (11-17行 As=O/P Co=R/S)
 P列 → 仮配（舗      (10-17行 As=R/W Coなし)
 R列 → 管工（舗50    (16-23行 As=R/T Co=V/X)
```

転記元の**ブロックの位置は自動で探す**。「□舗装版破砕」を見つけ、その下の
「種別・舗装厚」と「合 計」の並びから列を決め、As / Co が続く行数を数える。
シートごとに列が違う（試掘は O/P、管工は R/T）ので、ここは固定できない。

行の終わりに**予備を1行足す**。次の工事で舗装厚が1種類増えても式を直さずに
済む。SUMIF は空欄に当たらないので、余分に含めても結果は変わらない。

## この工事での結果

| 項目 | 値 |
|---|---|
| 舗装版破砕の行 | 55行（13〜67行） |
| 書き込むセル | 91個 |
| うち既にリンクがあった | 16個 → **15個は値が同じ**、1個が下記 |
| うち空だった | 75個 → 74個は 0、1個が下記 |
| 見送り | 1個（`仮配（舗` に Co 側の欄が無い P67） |

13〜25行は J・K・L・M・N の**全部**に入る（50個）。

| 行 | 厚さ | 種別 | J | K | L | M | N |
|---|---|---|---|---|---|---|---|
| 13 / 14 / 15 / 18 / 19 / 21 | 4・5・10・14・15・20 | As | ● | ● | ● | ● | ● |
| 22 / 23 / 24 / 25 | 4・8・15・20 | Co | ● | ● | ● | ● | ● |

## 見つかった不整合

`試掘（舗50` には 5cm が無く、`P12` は **10cm** の数量（1.2）。
ところが総括表の **J14（I列=5cm）** がその `P12` を参照している。
本来 1.2 は **J15（I列=10cm）** に入るべき値。

計の行（17行目）で合算されるので総量は合っているが、厚さ別の内訳が
1段ずれている。舗装版破砕は厚さで単価が変わるので要確認。

マクロを流すと **J14 が 0 になり、J15 に 1.2 が入る**。ここだけは値が
動くので、「計」の行が前と変わっていないことを確かめてほしい。

## うまくいかなかったとき

1つも書き込めなかった場合、マクロはどこで止まったかを出す。

```
　舗装版破砕 の行 … 55 行
　うち舗装厚が読めた行 … 37 行
　うち種別(As/Co)が読めた行 … 37 行
　黄色い入力セル … 92 個
　ブロックが見つかった転記元 … 11 / 11 シート

0 になっている項目が原因です。
```

黙って何もしないことはない。

## 検証について

- `excel/docs/verify_hasai.py` … **マクロと同じ判定を Python に写したもの**
  91セル分の数式を出し、J14 が指示どおりの文字列かを確かめる
- `excel/docs/lint_vba.py` … 予約語・宣言位置・構文の機械チェック

```
python3 excel/docs/verify_hasai.py
python3 excel/docs/lint_vba.py
```

**VBA 自体を Excel で走らせた確認はしていない**（作成環境に Excel が無い）。
